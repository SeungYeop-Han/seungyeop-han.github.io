원티드 포텐업 - 네 번째 LXP 프로젝트 회고

DDD, 헥사고날, MSA 까지 다양한 것들을 훑어보면서 느낀 경험들

회고 작성 중 …

느낀점, 개선해야 할 포인트

  • 게이트 웨이에서 엔드 포인트 관리가 너무 어려움. 엔드포인트 수정 또는 추가 될 때마다 매번 추가해야 해서 번거로웠음. 다음 부터는 각 서비스에서 공개할 엔드포인트 url 을 /public 을 붙여서 공개하면 게이트웨이 수정 없이 가능할 듯.
  • MSA 에서는 정말로 테스트가 필수! 디버그 하는게 너무 어렵다. 환경 뜨는 것도 한 세월이니 수정 반영도 느리기 때문에 각 서비스가 정말 철저하게 테스트를 한 후 합쳐야 한다. 특히 서로 간 통신에 대한 문서 역시 만들어 놓아야 한다는 것을 느꼈다. api 문서는 프론트에게 공개되는 api 에 대해서만 작성해야 하는 것이 아니라 서비스 간 통신에 대해서도 작성되어야 한다.
  • 또한 설정 정보 불일치에 의한 문제도 있었다. 중앙 config 서버의 필요성을 체감할 수 있었다.
  • 디버그를 위한 로그 전략, 스택 트레이스 필수, 어디서 어떤 문제 발생했는 지 바로 알 수 있도록 디버깅 로그 남기는 데 더 노력을 기울여야 한다. 로그에 spanId 붙여서 전파하는 식으로?
  • 환경이 뜨는 것이 느려서 불편했음, 더 빠르게 환경을 띄우는 법이 있을까?
  • 자바에서 NPE 가드를 필요한 지점에 넣기가 힘들다. 어떤 파라미터가 null 일 수 있는 지 일일히 고려하면서 코드를 작성하는 것이 힘들기 때문이다. 특히 헥사고날 아키텍처를 사용하고 있는 현 상황에서는 더욱 그렇다. 작성해야 할 코드의 절대적인 양도 많을 뿐더러 매핑 로직이 많기 때문에 특정 NPE 관련 문제가 매핑 로직을 타고 전파되는 경우가 많다.
    • 타입 수준에서 Not Null 타입을 선언하고, 컴파일 시점 에러를 발생시킬 수 있어야 한다 (코틀린처럼). JSpecify 나 uber nonnull? 프레임워크 사용하면 되는 것 같던데 이번에 조사해보자
  • 테스트 워크 플로우 만들어야 한다. 아직도 단위 테스트 하는 게 어렵게 느껴진다. 특히 mocking 하는 게 아직도 익숙하지 않다.
  • 헥사고날의 매핑 지옥을 조금이라도 해소하기 위한 전략이 필요하다고 느낌. 일단 코드 외적으로는 AI 를 적극적으로 사용하는 것이 좋다고 느낌. 매핑 로직은 로직 자체가 어렵다기 보다는 번거롭고 헷갈리는 것이기 때문에 AI 활용을 적극적으로 해야한다. 이때 어떤 정보를 줘야 하는 지 미리 템플릿을 정리해두고 codex cli 등을 활용해보자.
    • DTO 를 이렇게 까지 세분화 할 필요가 있었을까?
